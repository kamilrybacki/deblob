# Fine-tuning the SLM for better schema Names + Umbrellas — Joint Research Report
run: `jr-slm-finetune-nu-211549` · 2026-07-21 · agents: Claude Code + Hermes

## Executive summary
**Naming: yes — pursue a small task-specialized 0.5B LoRA, but MEASURE FIRST.** A specialized 0.5B can beat a general 0.5B on this bounded, structured task, and — critically — lets Deblob **drop the few-shot block and shrink the prompt**, which is the real path to fitting the CPU budget the model currently times out on. But `[H]` a LoRA is **not faster per token** (same layers/params/bandwidth); the end-to-end win comes only from shorter prompt + fewer output tokens + no output-repair retries. So the mandatory first step is to **decompose the current timeout** (queue wait / load / prompt-eval / eval / controller) — if cold-load or contention dominates, a naming LoRA will be more accurate and still time out.
**Umbrellas: mostly NOT a fine-tuning problem** `[C+H, high]`. Umbrella quality lives in deterministic eligibility/cannot-link gates + retrieval + prior approved mappings + type/unit/cardinality/grain/temporal checks + finite candidate construction + HITL. Fine-tune ONLY the thin finite-hypothesis **adjudicator** (rank legal candidates, EXACT vs RELATED/NARROWER/BROADER, hard-negative discrimination like event-time vs ingestion-time, abstain). If retrieval recall is poor, no adjudicator fine-tune recovers the missing candidate.
**Data: the governance loop already mints the gold set** `[C+H]` — human name edits and umbrella approve/reject are exactly preference data. Deblob's `name_meta` already stores the drafts (`heuristic`, `slm_raw`) next to the human name → free SFT + DPO pairs. **Serving:** merge the adapter into a GGUF and import as a distinct Ollama model (not runtime adapter-swap). **Distillation:** defer; use a frontier/1.5B teacher only to *augment* if human gold is thin. **1.5B:** shadow/teacher only — ~half the CPU throughput, wrong fix for a synchronous timeout.

## Key findings

### Is fine-tuning the right lever for NAMING?
- **A specialized small model beats a general one on bounded structured tasks** `[C+H, high]`. Task-specific SLMs (0.5–3B) dominate the Performance-Efficiency Ratio and, when fine-tuned, beat frontier models on narrow structured tasks (function-calling, extraction, classification) — a fine-tuned Qwen3-0.6B beat every frontier model on Smart-Home tool-calling on both quality AND efficiency `[C]` (distil labs; arXiv 2603.21389, 2512.15943). Structured-interpretation with SLMs gives tight, bounded tail-latency, sharpest under schema-constrained decoding `[C]` (jdit.v2i2.272).
- **BUT naming has a free-form component → moderate, not dramatic, gains** `[C]`. The "docstring boundary case": a name is part-templated (source + head noun) and part free-form — free-form description "requires broad reasoning, harder for a small model; fine-tuning helps less" (distil labs). Deblob's heuristic already covers the templated part, so the SLM's marginal job is the hardest part.
- **The latency win is real but indirect** `[C+H]`. `[C]` A fine-tuned model needs no few-shot exemplars → the prompt collapses from (system + 4-shot + fields) to (short instruction + fields), and CPU cost scales with prompt tokens. `[H]` sharpens: per-token speed is unchanged; the end-to-end win is prompt shrink + fewer output tokens + no malformed-output repairs + reliable stop. `[H]` It will NOT fix cold model load, Ollama queueing, CPU throttling, oversized KV, eviction, or an undersized request timeout — **decompose the timeout before training.**
- **Break-even is low; bootstrap by distillation** `[C]`. Specialized small models beat general with 100–500 labels; to beat a *strong instruction-tuned* baseline can need ~5k (EMNLP 2025.9). `[H]` recommends ~300–500 deduplicated high-quality labels to start, 1000+ preferred. Cold-start via teacher-generated synthetic names over existing + synthetic schemas (arXiv 2410.18588; OpenReview efficient-distillation) — but `[H]` teacher output is a *weak* label until deterministically or human-validated.

### Umbrellas — fine-tune problem or retrieval problem?
- **Retrieval + deterministic rules + HITL are the quality mechanism; the SLM is a thin adjudicator** `[C+H, high]`. `[H]` The SLM should only: rank already-legal candidates, distinguish EXACT_EQUIVALENT from RELATED/NARROWER/BROADER, discriminate hard negatives (event vs ingestion time), select among approved vocabulary labels, and abstain — never generate unrestricted clusters/transforms/units/mappings/promotions. This matches Deblob's existing `Adjudicator` + `DeterministicAnchor` + finite-hypothesis design `[C]`. LLM schema-matching research points the same way: retrieval/candidate-generation dominates (Magneto, ReMatch, Schemora, KcMF) `[H]`.
- So umbrella fine-tuning has a **much lower ceiling** than naming, and only pays off after retrieval recall is already good.

### The training loop + data
- **The feedback→JSONL→Modal-LoRA loop already exists and extends cleanly** `[C, code-verified]`: `deblob-slm::feedback::LabelSource`, `FeedbackStore::export_jsonl`, `retrain::ReplaySet::to_jsonl`, `deblob_eval::render_finetune_jsonl`, and a real `FineTuneHook` that writes JSONL for the Modal T4 trainer (`deploy/experiment/modal/trainer.py`). Adding naming/umbrella = new `LabelSource` variants + new JSONL renderers, same pipeline.
- **Human edits are preference data — with caveats** `[C+H]`. `[C]` "Draft = rejected, human edit = preferred" is textbook DPO, effective with few pairs (NeurIPS 2025 user-edits; OpenPipe; DPO 2305.18290). Deblob's `name_meta` already carries `heuristic`/`slm_raw` (rejected) vs the human `label` (chosen). `[H]` CRITICAL caveats: **"not edited yet" is NOT approval** (don't treat un-touched auto-names as positives); retain proposal + evidence packet + revision history; for umbrellas capture a **rejection-reason taxonomy** (wrong concept / wrong grain / unit conflict / insufficient evidence / duplicate) + hard negatives; **split train/eval by source/family/umbrella lineage AND time to prevent leakage**; use **active learning** (route boundary-uncertain proposals to review, not easy labels).

### Serving on Ollama (CPU)
- **Merge the adapter into a GGUF; don't runtime-swap** `[C+H, high]`. `[H]` pipeline: LoRA → merge into pinned HF Qwen base → GGUF → quantize → import as a distinct Ollama model; keep the raw adapter for audit; unmerged adapters for shadow only until llama.cpp/Ollama-version compatibility is proven (adapter swap causes load/eviction latency).
- **0.5B stays on the live path; 1.5B is shadow/teacher only** `[H]`. Directional community CPU numbers: 0.5B ≈ 58 tok/s (~1 GiB) vs 1.5B ≈ 25.65 tok/s (~3.88 GiB) — 1.5B ≈ half the throughput, wrong remedy when 0.5B already trips a *synchronous* circuit breaker.

## Conflicts & adjudication
**Per-task LoRA vs one multi-task adapter.** `[C]` My sources argue a single unified adapter (adequate rank) matches multi-adapter with less latency, and MTL is more maintainable/extensible for small models ("Align, Don't Divide" 2508.05078; Adapter-Efficiency ACM 3632463). `[H]` argues **separate adapters are the safer INITIAL design** — naive multi-task risks interference on a 0.5B (LoRI 2504.07448; MTL-LoRA AAAI). **Resolution:** not contradictory once phased. **Start per-task** (naming and umbrella-adjudication are different jobs; isolating them makes evaluation clean and avoids early interference); **once each clears its gates, consolidate** to a single multi-task adapter or two merged GGUFs for serving simplicity. Both agree the served artifact is a *merged* GGUF, so serving cost is identical either way — the choice is purely a training/eval hygiene decision, and per-task-first wins for a first experiment.

## Recommended plan (phased, measure-gated)
0. **Diagnose first `[H]`** — decompose the live naming timeout into queue / load_duration / prompt_eval_duration / eval_duration / controller-end-to-end over ≥10 warm+cold runs. If cold-load/queue/KV dominates, fix serving (keep-alive, resource limits, timeout, warm pool) BEFORE any training.
1. **Compact-prompt baseline (no training)** — drop the few-shot block, shrink the instruction, keep constrained JSON decoding; benchmark quality + warm/cold p95 vs today's few-shot and heuristic-only. This alone may reclaim the SLM within budget.
2. **Naming LoRA** — collect ~300–500 (→1000+) deduplicated gold names (human edits = chosen; `heuristic`/`slm_raw` = rejected → SFT + DPO), bootstrap with teacher-generated + deterministically-validated synthetic names; train on Modal T4 via the existing loop; **merge → GGUF → quantize → Ollama**; evaluate the *final GGUF*.
3. **Umbrella adjudicator LoRA (later)** — only after retrieval recall is good and several hundred approve/reject/abstain examples with hard negatives exist; fine-tune ranking/relation/abstain only, never generation; HITL invariant unchanged.
4. **Gates `[H]`** — naming format-validity ≥99.5%; zero unlicensed concepts post-deterministic-gate; blinded human-preference win over the heuristic; no hard-negative regression; warm+cold p95 under the circuit-breaker budget with ≥20% margin; umbrella HITL invariant intact; sealed hard-negative eval with a reported false-positive bound.
