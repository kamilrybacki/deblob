# Read-only MCP context layer over Deblob — Joint Research Report
run: `jr-deblob-mcp-212343` · 2026-07-21 · agents: Claude Code + Hermes

## Executive summary
**Build a thin, separate `deblob-mcp` service that wraps Deblob's fixed `GET /api/v1` routes as ~8 bounded read TOOLS, and register it in cellarette exactly like `discord-mcp`.** Two homelab constraints from reading cellarette's own code decide the shape and override the generic MCP best-practices `[H, code-verified]`: (1) **cellarette proxies `tools/list`/`tools/call` but NOT MCP resources** (its shared result type doesn't even model `structuredContent`) — so the textbook "expose entity reads as `deblob://schema/{id}` resources" is a dead end through the aggregator; **tools-only for v1**. (2) **Wire format = compact JSON in `TextContent`, not Markdown** — Deblob's payload is IDs, similarity scores, cursors, lineage edges and evidence masks, which JSON represents faithfully and Markdown mangles. Everything else both agents already agreed on: no Rust-binary integration, no mutation tools, orchestrate multi-hop server-side, page fields independently, default lists to 10 (cap 50), return compact schema *cards* + explicit typed *edges* instead of recursively embedding whole records, and enforce read-only as a **structural GET allow-list** (not merely MCP annotations), since Deblob has a single shared bearer tier.

## Key findings

### The MCP surface — tools-only, orchestrated, bounded
- **Resources are unavailable through cellarette → tools-only** `[C+H, H decisive]`. The generic guidance is strong that read-by-id belongs in *resources* (`deblob://schema/{id}`) to save tool-call slots (WorkOS, MCP spec, llmbestpractices) `[C]`. But Hermes read cellarette's `mcp-proxy.ts`/`profile-registry.ts`/`shared.ts` and confirmed it forwards only `tools/list` + `tools/call` and has no `structuredContent` in its result type `[H]`. So resource templates would never reach a cellarette-connected agent. **v1 is tools-only**; resources become an option ONLY if a client ever connects to `deblob-mcp` directly (bypassing cellarette).
- **~8 bounded read tools** (both converged on nearly the same set; `<action>_<resource>` snake_case, one `deblob` server = one domain = one auth boundary) `[C+H]`:
  - `find_schemas(query?, source?, field?, limit=10, cursor?)` — entry point; returns compact cards + `has_more`/`next_cursor`.
  - `get_schema_context(schema_id)` — the **orchestrated hub**: name+source+name_source, field summary, semantic fingerprint, privacy class, value-profile summary, AND the typed edges (family_id, source_id, umbrella membership, top neighbor schema_ids) in ONE call. Server does the multi-hop so the agent doesn't `get→list→get` (googleapis mcp-toolbox: "orchestrate internally") `[C]`.
  - `get_family_versions(family_id)` · `get_semantic_neighbors(schema_id, limit)` — the **traverse verbs** (similarity edges).
  - `list_umbrellas(state=active)` · `get_umbrella_context(umbrella_id)` — gold contract + member schemas + child field-maps (lineage).
  - `list_schema_fields(schema_id, cursor?)` — fields paged independently (a wide schema shouldn't blow the budget).
  - `get_source_context(source_id)` — ingest lineage + the schemas discovered from it.
- **Parameterized traversal tools, not query-language** `[C+H]`. KG-over-MCP consensus: expose pre-defined traversal (`get_semantic_neighbors`, `get_umbrella_context`) so the graph stays canonical and the agent stays grounded — LLM-generated Cypher/SPARQL fails 30-50% on multi-hop (llms3, Neo4j, PuppyGraph, Atlan) `[C]`. Closest analogue is **DataHub MCP**: search + batched entity retrieval + pageable fields + bounded lineage traversal `[H]`.

### Token / context discipline
- **Compact cards + typed edges, never embedded records** `[C+H]`. `get_schema_context` returns edge *ids* (neighbor schema_ids, umbrella_id, source_id), not the neighbors/umbrella/source expanded inline — the agent walks the edge with a follow-up tool only if it needs to `[H]`. Default 5-ish fields per card, on-demand detail (Anthropic: ~⅔ token cut from default-lean + detail-on-request) `[C]`.
- **Pagination everywhere** `[C+H]`: `limit` (default 10, cap 50), `cursor`/`next_cursor`, `has_more`, and a truncation-steer message ("Results truncated — narrow the query or raise limit"). Keep the toolset in the 5-8 range (≤40 hard cap) to stay under the tool-selection accuracy budget (googleapis style-guide, Anthropic, AWS) `[C]`.
- **Wire format = compact JSON in `TextContent`** `[H, adjudicated]`. Generic advice leans Markdown for LLM-native reading (good for prose/docs) `[C]`, but Deblob's data is structured (schema_ids, cursors, similarity scores, lineage edges, numeric-bucket evidence) — JSON keeps it faithful and parseable; Markdown would blur ids/scores. Reconciled: **JSON payload**, optionally prefixed by one short human-readable summary line per entity.

### Homelab delivery — clone the discord-mcp backend
- **Exact pattern** `[H, code-verified]`: Deployment in ns `mcp-servers`; **Streamable HTTP `/mcp` on port 8000**; **headless ClusterIP** Service; **cellarette-only NetworkPolicy** ingress; register as an `mcp_proxy` named **`deblob`** (→ tools surface as `deblob__find_schemas`, etc.); Deblob bearer held in a **Secret, never passed through from the caller**; **no NodePort**. (SSE HTTP+SSE transport is deprecated; Streamable HTTP is correct) `[C]`.
- **Kairos correction** `[H]`: kairos was a cellarette *consumer* (the `kairos-ro` profile), NOT an MCP backend — and both its chart and that profile were since removed. So `discord-mcp` (and the `mcp-servers`/`discord-mcp` chart) is the ONLY live reference backend to copy. (This corrects the brief's assumption.)
- **Read-only enforced structurally** `[H]`: a fixed GET allow-list in the wrapper — the process literally cannot issue a non-GET — plus the NetworkPolicy boundary, because Deblob exposes a single bearer tier (the same token can write). MCP `readOnlyHint` annotations are advisory only and are NOT the control.
- **Never expose** `[C+H]`: raw payloads (Deblob never persists them), `/candidates/{id}/samples` (redacted-but-sensitive, separately gated — leave it out of the read-only layer), `/stream` SSE (don't tunnel a long-lived stream through a tool call; add a bounded cursor-based event tool later if event consumption is ever needed), quarantine raw bodies.

## Conflicts & adjudication
1. **Resources vs tools for entity reads.** `[C]` external best-practice: entity-by-id → MCP *resource* (`deblob://schema/{id}`) to avoid spending a tool slot per read. `[H]`: cellarette can't proxy resources at all. **Winner: Hermes / infra reality** — tools-only for the cellarette path; the "resource" idea is parked for a hypothetical direct-connect client. Not a real conflict once the aggregator's capabilities are known.
2. **Markdown vs JSON wire format.** `[C]` sources lean Markdown (LLM-native). `[H]`: JSON for structured graph data. **Winner: Hermes for this data type** — Deblob is ids/scores/edges, not prose; compact JSON (± a one-line summary) is more faithful and cheaper to act on.
